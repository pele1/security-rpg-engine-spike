# Engine Spike Test Plan

## Purpose

Run the same tests against the RPGJS and GDevelop implementations of **Badge Incident**. Record evidence and limitations in `docs/FINDINGS.md`.

## Test 1 — Local start

**Goal:** Confirm a new contributor or coding agent can start the implementation from repository instructions.

Record:

- prerequisites;
- commands or editor steps;
- whether manual project repair/import was needed;
- time-consuming surprises.

Pass: the game can be launched locally from a documented reproducible process.

## Test 2 — Isometric scene

**Goal:** Verify the required presentation rather than a fallback orthogonal map.

Check:

- scene clearly reads as isometric;
- player aligns naturally with the isometric environment;
- walls/props/door do not exhibit obviously broken depth ordering;
- collision/navigation is usable.

Pass: the scene is convincing enough to serve as the basis for the intended small isometric RPG.

## Test 3 — Core scenario

Play all required paths from `shared/SCENARIO.md`:

1. Admit the visitor directly.
2. Redirect the visitor to reception.
3. Ask who the visitor is meeting, then choose a follow-up path.

Pass: branches produce the specified state changes and distinct contextual outcomes.

## Test 4 — Shared-data traceability

**Goal:** Determine whether a reviewer can understand where game semantics live.

Inspect the implementation and answer:

- Where is each dialogue line stored?
- Where are choices defined?
- Where are flags/conditions defined?
- Where are character-to-asset mappings defined?
- Is `shared/scenario.json` consumed directly, transformed at build time, or duplicated manually?

Pass: the relationship between shared semantics and runtime behavior is explicit and maintainable.

## Test 5 — External asset replacement

Replace one character visual and one sound with files of the same logical role.

Pass if replacement can be completed without recreating the scenario in the editor and without embedding the asset into an opaque database.

Record whether filenames, metadata, import files, or editor regeneration were required.

## Test 6 — Mandatory AI change test

Perform the following change using only repository-accessible files and coding-agent tooling. Do not manually edit the game through a visual editor during this test.

> Add a developer NPC named Daniel near the secure door. If the player asks Daniel about the visitor, Daniel says he does not know them. This unlocks a new visitor dialogue option. Add an external placeholder asset reference for Daniel.

Required behavior:

- Daniel appears near the secure door.
- Daniel can be interacted with.
- Before speaking to Daniel, the new visitor dialogue option is unavailable.
- Speaking with Daniel sets a persistent scenario flag.
- The new visitor dialogue option then appears.
- Daniel's visual uses an external asset or placeholder file/reference.

Record:

- all changed files;
- lines added/removed where practical;
- whether a large generated project file changed;
- whether the coding agent could reason about the modification without editor-specific knowledge;
- any manual cleanup required.

This test receives special weight because agent editability is the primary experiment goal.

## Test 7 — Map change test

Using repository/code tooling where possible, add a small meeting room next to the reception area with two visible entrances or openings.

The objective is not artistic quality. It is to learn whether map structure is practically agent-editable.

Record:

- file formats modified;
- whether coordinates are understandable;
- whether a visual editor was necessary for final correction;
- whether the resulting diff is reviewable.

A manual visual-editor refinement is allowed after the repository-only attempt, but must be documented separately.

## Test 8 — Static production build

Create the production build intended for web hosting.

Pass criteria:

- output contains an entry page/assets suitable for HTTP static hosting;
- no application backend is required;
- scenario is playable in the production build;
- relative asset paths work when hosted from the documented base path.

Record exact build command/process and output directory.

## Test 9 — Repository diff quality

Review the diffs generated by Tests 5–7.

Rate 1–5:

- readability;
- locality of change;
- generated noise;
- merge-conflict risk;
- ease of code review.

## Test 10 — Developer/agent experience

Rate 1–5:

- documentation clarity;
- setup complexity;
- amount of engine-specific knowledge required;
- speed of iteration;
- debugging quality;
- suitability for future AI-driven scenario generation.

## Evidence format

For each engine, add a section to `docs/FINDINGS.md` containing:

- environment/version tested;
- test result: Pass / Partial / Fail;
- brief evidence;
- important changed files;
- workaround, if any;
- score impact.

Do not score an untested assumption as a success.
